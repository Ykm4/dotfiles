# マークダウン記法規約

すべての作業で出力するマークダウン（ドキュメント・PR説明文・Issue本文・チャット応答・コミット本文など）に適用する。日本語テキストの書き方を統一するための規約。

---

## 箇条書きの句点ルール（文化庁「公用文作成の考え方」準拠）

- 箇条が名詞・体言止めで終わる場合は句点（。）を付けない。
- 箇条を文として書く場合は、原則として「1箇条 = 1文」とし、文末に句点を付ける。
- 1箇条の中に複数文を詰め込まない。
- 独立した内容は同階層の箇条に分割し、サブ箇条は補足にのみ使う。

体言止めと文形式は同一リスト内で混在してよい。文形式の箇条にだけ句点が付く。

```markdown
- dependabot.yml の流量を絞る設定変更
- 適用後に手動 Check for updates で初回 PR を確認する。
- security alerts のトリアージ
```

## 箇条書きの階層

- 箇条書きは原則1階層とする。
- 補足が判断に必要な場合のみ、1段だけネストする。

## 番号付け・選択肢ラベル

- 囲み数字（①②③④⑤⑥⑦⑧⑨⑩）は使わない。
- 代わりに半角ブラケット形式`[1]` `[2]` `[3]`を使う。
- アルファベットで区別したい場合は`[A]` `[B]` `[C]`を使う。

理由: 囲み数字は環境（フォント・ターミナル）によって視認性が落ちる。半角ASCIIは環境非依存で安全。

```markdown
良い: 次のアクション候補 — [1] 削除、[2] アーカイブ、[3] 名前変更
悪い: 次のアクション候補 — ① 削除、② アーカイブ、③ 名前変更
```

## バッククォートの使用範囲

- バッククォートはコード識別子・ファイルパス・コマンド・設定キーに限定する。
- 機能名・固有名詞・製品名は地の文で書き、バッククォートで囲まない。

```markdown
良い: dependabot.yml の `open-pull-requests-limit` を 5 にする
悪い: `Dependabot` の `流量制御` を行う
```

## コード内コメントの日本語の折り返し

- コード内コメントの日本語は、文の途中で折り返さない。
- 行を分けるときは句点（。）の直後で分け、行の長さはエディタの折り返し表示に任せる。

理由: 固定幅での機械的な折り返しは語句の途中で行が切れて読みにくく、機械層（textlint）はコード内コメントに届かないため修正もできない。

## 日本語の文章作法（「公用文作成の考え方」を参考）

コード、引用、固有名詞、製品名、既存の用語集やコードベースで定着した表記（外来語の長音の有無を含む）は、この規約より優先し、変更しない。

- 形式名詞と補助的な用法は、実質的な意味を表す場合を除き、原則としてひらがなで書く（こと・とき・ため・とおり・もの・ほか・できる・ない・〜ていく・〜てくる・〜てみる・〜ておく・〜てください・〜ていただく）。
- 一文を短くして論点を原則1つに絞り、3つ以上の項目を列挙するときは箇条書きにする。
- 本文の文末は、引用、従属節、体言止めの箇条書きを除き、文書内で敬体（です・ます調）か常体（である調）に統一する。
- 結論または依頼を先に示し、理由や詳細を後に書く。
- 主語と述語、修飾語と被修飾語を対応させ、係る語と受ける語を近くに置き、二重否定や不要な受け身は避ける。

## 和英混在を避ける

日本語の文に英単語を混ぜた分かりづらい表現を避ける。判断基準は「日本語話者が読んで、日本語へ直したほうが分かりやすいか」とし、迷うときは日本語にする。適用範囲はPR説明文・Issue本文・design doc・changesログ・コメント・報告など日本語の文章全般とする。

- 日常語や一般的な動作・状態・概念を表す英単語で、定訳や自然なカタカナ語があるものは日本語にする。
- 技術分野で日本語化されず定着した用語・略語、固有名詞・製品名・機能名、バッククォートで囲む識別子・設定キーはそのまま使う。

## 伝わらない比喩・内輪の言い回しを避ける

読み手が文脈を共有していないと意味の取れない比喩や内輪の言い換えを避け、指している状態や事実を具体語で書く。判断基準は「その分野の用語として定着しているか」とし、定着していない比喩は書き下す。適用範囲は和英混在と同じく日本語の文章全般とする。

- 状態を比喩で言い換えず、その状態をそのまま書く（参照されなくなった・未使用になった・対応する定義が無くなった、など）。
- 孤児プロセスやorphan branchのように、その分野の用語として定着した用法はそのまま使う。
- チーム内でだけ通じる略語や言い換えは、初出で正式名称を書く。

理由: 比喩は書き手には短く便利だが、読み手が同じ連想を持たなければ意味が変わる。レビューや引き継ぎでは読み手を選べないため、具体語のほうが安全である。

```markdown
良い: 参照されなくなった型宣言を削除する
悪い: 孤児になった型宣言を削除する
```
