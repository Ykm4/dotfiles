# 調査結果・集計レポートをまとめる

調査結果の価値は「何が分かったか」より「どこまで確かか」にある。断定と推測を混ぜない形で見せる。

## 材料を確度で仕分ける

書き始める前に、手元の情報を3つに分ける。

- 一次情報で裏が取れたもの（公式ドキュメント、実測値、実際に叩いたAPIの応答）
- 二次情報どまりのもの（ブログ、まとめ記事、他者の報告）
- 調べたが分からなかったもの

3つ目を省かない。「調べた範囲では不明」は結果である。

## 判断の軸を先に決める

比較表の列は、読者が実際に判断に使う軸だけにする。集めやすかった項目を並べない。

判断を伴う調査なら、結論を冒頭に置く。読者が結論だけ読んで離脱しても、それが正しく伝わる形にする。

## 本体を組む

- 冒頭に`.verdict`で結論。先頭に`.verdict-label`（例「結論」）を置く
- 比較表。数値列は`td.num`。判定は`.chip.on`（可）と`.chip.warn`（注意）で示し、チップの中に語（可・不可・条件付き）を必ず書く。色だけで区別しない
- 判断を左右する落とし穴は`.note`に切り出す。ライセンス、価格改定、提供終了、法令の適用条件など
- 図が構造を持つ場合のみ図にする。比較表で足りるものを無理に図にしない
- 出典。URLと取得日を明記する。実測値なら測り方も書く
- 未確認事項

## 数値の扱い

- 取得日を必ず書く。星数・価格・為替・税率は時点で変わる。
- 出所を書く（公式ドキュメント・APIの実測・記事の引用）。
- 単位を揃える。桁が大きい数は`Intl.NumberFormat`の形式で区切る。
- 概算には「約」を付ける。実測と概算を同じ表に並べるときは列や注記で区別する。
- 合計額など見出し級の単独数値には`tabular-nums`を付けず、明朝も当てない。

## 見せ方の型

| 見せたいもの | 型 | 手段 |
|---|---|---|
| 選択肢の比較 | 表 | HTML `table` |
| 費目・構成の内訳 | 円 | Mermaid `pie` |
| 月次などの推移 | 折れ線・棒 | Mermaid `xychart-beta` |
| 位置づけの比較 | 4象限 | Mermaid `quadrantChart` |
| 多軸の評価 | レーダー | Mermaid `radar-beta` |
| 大小の比較・順位 | 横棒つき表 | `parts.md`の部品 |
| 増減の要因分解 | ウォーターフォール | `parts.md`の部品 |
| 内訳の推移 | 積み上げ棒 | `parts.md`の部品 |

グラフが要るときは自動注入されるChart.jsも使える。1ページ1枚、`type`は`line` `bar` `donut`の3つだけである。2枚目以降が要るなら`parts.md`の部品か素のSVGを書く。

二軸グラフは使わない。単位が違う2系列は2枚に分けるか、起点を100に指数化する。

## 固有の自己点検

`authoring.md`の点検に加えて確認する。

- 判定が色だけでなく語でも読めること
- 出典のURLと取得日が入っていること

## 公開したあと

調査対象がノートに残す価値のあるものなら、`note`スキルでリポジトリにも記録することを提案する。アーティファクトは見せるためのもの、ノートは残すためのもので、役割が違う。

## 注意

- 出典を確認していない主張を書かない。「〜と言われている」で逃げない。
- 反対の結論を支持する材料があれば必ず載せる。
- 都合の良い材料だけ並べた比較表は判断を誤らせる。
- 取引先名・未公開のメールアドレス・GCPのプロジェクトID・秘密情報を載せない。
- 共有される可能性がある成果物として扱う。
