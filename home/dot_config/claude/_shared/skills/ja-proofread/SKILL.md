# ja-proofread — 自然な日本語かをサブエージェントで点検する

AIが生成した日本語は、意味は通っても不自然になりやすい。過剰な太字強調、冗長なヘッジ表現(「〜かもしれません」「〜と思われます」)、定型的な前置き、箇条書きの不統一、同じ語尾の連続などが典型。このスキルはサブエージェントを1つ起動し、対象テキストを規約準拠と自然さの両面で点検して、確実な修正を適用しdiffで報告する。

中核の原則は次の3つ。

- 分業する。決定的に機械化できる指摘(囲み数字→ブラケット・表記ゆれ・太字の乱用・スペース)はtextlintに任せ、本スキルは文脈判断が要る自然さ・文体・構成に集中する。
- 意味を変えない。修正は最小限とし、原文の主張・ニュアンスを保つ。過剰な書き換えをしない。
- 適用してから報告する。機械層のfixと確実な指摘はファイルへ自動適用し、変更をdiffで報告する。断定できない「任意」の指摘は適用せず提案に留める。

## いつ使う / 使わない

使う場面:
- 日本語のMarkdown・ドキュメント・PR説明・Issue本文・コミット本文を公開/提出する前の推敲
- 「AIっぽい」不自然な日本語を自然にしたいとき
- 記法規約(体言止め箇条の句点・結論先出し・和英混在等)に沿っているかの確認

使わない場面:
- 英語など日本語以外の文章(対象外)
- 囲み数字や表記ゆれの機械的な一括修正だけが目的のとき → textlintを直接使う(下記)
- コードそのもののレビュー(別の関心事)

## 対象の決め方

引数を次のように振り分ける。

- ファイルパス → そのファイルを対象にする。
- 文字列(貼り付け) → その文字列を対象にする。
- 省略 → 直近にこの会話で生成した日本語テキスト(応答・ドキュメント)を対象にする。

## Step 1: 機械層の修正を先に適用する(ファイル対象時)

対象がファイルなら、先にtextlintの自動修正を適用し、残った指摘をJSONで取得してサブエージェントの材料にする。これで重複指摘を避け、精度が上がる。

```bash
mise run textlint -- --fix <file> 2>/dev/null || true
mise run textlint -- --format json <file> 2>/dev/null || true
```

miseタスク`textlint`が未定義・失敗するときや、対象が文字列のときはこのStepを飛ばす。残ったJSONの指摘は「機械層で検出済み(自動修正不可)」として次のStepのサブエージェントに渡す。

## Step 2: サブエージェントで自然さ・文体・構成を点検する

サブエージェントを1つ起動する(Agentツール)。プロンプトには次を含める。

- 規約は`~/.claude/rules/markdown.md`を読んで正典とすること(推測で規約を作らない)。
- 対象テキスト(またはStep 1のtextlint JSON指摘)。
- 点検の観点(下記)。
- 出力形式(下記)。

点検の観点:
- 規約準拠 — 体言止め箇条は句点なし/文形式の箇条は句点あり、箇条書きは原則1階層、囲み数字を使わず`[1][2]`、バッククォートはコード識別子・パス・コマンド・設定キーに限定、形式名詞はひらがな、敬体か常体で統一、結論を先に、一文一論点、二重否定や不要な受け身を避ける、和英混在を避ける。
- 自然さ(AIっぽさ) — 過剰な太字強調、冗長なヘッジ表現、定型的な前置き・締め、同じ接続詞や語尾の反復、意味の薄い強調語、機械的に整いすぎた列挙。
- 語の伝わりやすさ — 専門用語として定着した用法(孤児プロセス等)を除き、読み手と文脈を共有していないと意味が取れない比喩的・内輪的な言い回し(参照されなくなった状態を指す「孤児」など)を具体語へ書き換える。
- 構成 — 結論・依頼が先にあるか、一文一論点か、係り受けが近いか。

サブエージェントへの指示で厳守させること:
- 意味を変えず、最小限の修正に留める。
- textlint(機械層)で直せる項目は指摘を重複させない。
- 断定できない指摘は「任意」と明示する。
- 粗探しをしない。指摘が少なければ少ないと正直に言う(件数を無理に増やさない)。
- 実態と明らかに矛盾する記述(古い手順の残骸など)に気づいたら「任意」として指摘してよい。

出力形式(サブエージェントに返させる):
- 指摘リスト — 各項目に [箇所] [分類(規約/自然さ/語の伝わりやすさ/構成)] [問題] [なぜ] [修正案]。
- 修正版 — 変更箇所のみをbefore/afterの対で列挙する(短いテキストなら全文でもよい)。長文で全文を再掲させるとトークンを浪費し、転記ずれの原因になる。

## Step 3: 確実な修正を適用し、diff で報告する

- ファイル対象なら、サブエージェントの確実な指摘をEditでそのまま適用する。承認待ちはしない。
- 適用した変更をdiff形式で報告する。機械層(Step 1)の自動修正分もあわせて要約する。
- 断定できない「任意」の指摘は適用せず、提案として分けて示す。
- 文字列対象は修正版を返すに留める(勝手にファイル化しない)。

## Step 4: 再検証する

ファイルへ適用した場合は`mise run textlint <file>`を再実行し、exit 0(機械層の指摘なし)を確認する。推敲の書き換えが新たな機械層違反(助詞の重複・スペース等)を持ち込むことがあるため。指摘が出たら直してから完了を報告する。

## textlint を直接使いたいとき

機械的な一括修正だけが目的なら、サブエージェントを介さずtextlintを直接使う。

```bash
mise run textlint -- --fix <file>   # 自動修正
mise run textlint <file>            # 指摘のみ
```

設定と対応ルールは`~/.config/textlint/README.md`を参照する。
